# DESIGN-SPEC — AI 知识库（开源 Wiki）

> 版本：v1.1 ｜ 日期：2026-08-15 ｜ 状态：定稿
> 本文档是项目唯一事实源。所有产出文档必须与本文档一致，冲突时以本文档为准。

## 一、项目定位

**「一线知识的沉淀与导航站」** —— 一个开源、Wiki 式、面向所有人的知识库。以 AI 领域为主体，架构支持扩展到任意知识领域。

- 形态：Wiki（点击词条跳转独立页面，互相链接）
- 受众：不只自己，开放给所有人阅读
- 部署：GitHub Pages（用户已确认部署在 GitHub）
- 语言：中文为主（词条定义中文，术语原文保留英文 + 全称）
- 扩展性：当前以 AI 领域为主体（机器学习/深度学习/NLP/CV/语音/RL/多模态/LLM/Agent/工程/安全伦理），架构支持扩展到任意知识领域。词条是独立节点通过 relations 连接，不受文件夹层级限制

## 二、核心设计：四根柱子

| 柱子 | 含义 | 机制 |
|------|------|------|
| **上限** | 内容能多深、多新、多一线 | 靠来源层级（一线来源优先，每词条带原始链接） |
| **标准** | 内容多规范、多可信、多一致 | 靠强制机制（Schema 校验、无源不收录、质量门） |
| **生态** | 内容产品活着 | 靠开放编写（四层贡献模型） |
| **信任** | 读者凭什么信 | 靠留痕（git 历史、来源标注、修订记录） |

## 三、双层结构

```
┌─────────────────────────────────────┐
│  前沿采集（社区感知层）                 │  ← 动态
│  · 自动扫描：GitHub 趋势 / arXiv 新论文│
│  · 大 V 推文 / Reddit / RSS 讨论       │
│  · 输出：新概念、新动向、争议话题       │
├─────────────────────────────────────┤
│  概念库（Wiki 沉淀层）                  │  ← 稳定
│  · 词条独立页 + 点击跳转 + 互相链接     │
│  · 每条标注：来源社区链接 + 收录时间    │
│  · 成熟度分层：[稳定] 已沉淀 / [热词] 社区热词  │
└─────────────────────────────────────┘
```

## 四、词条 Schema（每条强制字段）

```yaml
---
term: LoRA                  # 术语名（英文原名）
full_name: Low-Rank Adaptation   # 全称
aliases: [低秩适配]              # 别名
category: 模型微调               # 分类
maturity: stable                # 成熟度: stable([稳定]已沉淀) / hot([热词]社区热词)
status: published               # 状态: draft / review / published
contributors: []                # 贡献者（GitHub 用户名）
sources:                        # 来源链接（强制，无源不收录）
  - https://arxiv.org/abs/2106.09685
  - https://github.com/microsoft/LoRA
related: [微调, PEFT, 蒸馏]      # 关联概念（跳转路由）
created: 2026-08-14
updated: 2026-08-14
revisions: 3                    # 修订次数
---
## 定义
（一段话，人话优先，避免术语堆砌）

## 详解
（2-5 段，深入但可读）

## 为什么重要
（给学习者的价值锚点）

## 争议 / 讨论（如有）
（社区争议点，正反观点 + 各自来源）

## 参见
（关联词条链接，[跳转到其他词条页](其他词条.md)）
```

### Schema 校验规则（强制）
1. `term`、`full_name`、`definition`、`sources`、`category`、`maturity` 六项**必填**，缺失即打回
2. `sources` 至少 1 条有效 URL（可点击、可验证）
3. `maturity: hot` 的词条必须在定义区顶部标注「[热词] 社区热词，未经沉淀，信息可能快速过时」
4. `related` 中的关联词条必须真实存在（或列入待创建清单）
5. 词条文件名 = 术语名（如 `LoRA.md`），避免特殊字符

## 五、成熟度分级

| 级别 | 状态 | 允许 | 必须标注 |
|------|------|------|---------|
| [稳定] 已沉淀 | stable | 完整定义 + 多源交叉验证 | 无 |
| [热词] 社区热词 | hot | 一句话定义 + 单一来源 | 「[热词] 社区热词，未经沉淀」 |

升级规则：hot → stable 需要 ≥2 个独立来源 + 维护者审校通过。

## 六、四层贡献模型

```
L1 读者：纠错 / 补充 / 讨论 → GitHub Issue（不能改，但能说）
L2 社区贡献者：提交词条草稿 → Pull Request（可以写，不能发）
L3 核心维护者（用户 + 审校 Agent）：合并 / 改稿 / 定稿
L4 机器（采集 Agent）：自动抓热词卡 → 只能进「采集/」目录（未沉淀区）
```

关键规则：**「可以写」不等于「能发」**。L2 提交的草稿自动过 Schema 校验——字段缺失、无来源、格式不对 → 自动打回（CI 校验）。任何人能提交，但只有过门 + 审校才能发布。

## 七、质量门流水线（内容进站四道门）

1. **起草**：AI / 贡献者写第一稿
2. **自动校验**：Schema 校验（必填字段 + 链接有效性 + 格式检查，CI 自动化）
3. **人工审校**：维护者（用户）审校——读感、判断、取舍
4. **定稿发布**：合并 → 站点自动重建

AI 生成内容标注 [AI]，人工审校过标注 [人]。

## 九、本次 Kimi Code 的任务（只做文档，不做站点生成器）

产出以下 4 个文件，写入 wiki 根目录：

1. **CONTENT-SPEC.md** —— 《内容规范 v1》：
   - 词条 Schema（按第四节，含 YAML frontmatter 示例）
   - 写作风格规范（人话优先、术语中文+英文原文、避免堆砌）
   - 成熟度分级规则（第五节）
   - 校验规则（第四节 Schema 校验规则，展开成可操作的检查清单）
   - 分类体系建议（参考：模型/架构/训练/推理/微调/工具/平台/对齐/上下文工程/多模态/Agent 等，给出 8-12 个分类）

2. **CONTRIBUTING.md** —— 《贡献指南》：
   - 项目介绍 + 双结构说明（沉淀层/采集层）
   - 四层贡献模型（第六节，详细展开每层的操作方式）
   - 新词条提交流程（Fork → 建分支 → 写词条 → PR → 过校验 → 审校 → 合并）
   - 词条写作模板（可直接复制的 .md 模板）
   - 行为准则（简短，友善协作）

3. **MAINTENANCE.md** —— 《维护流程》：
   - 审校流程（质量门四步，第七节）
   - 发布流程（合并 → CI → Pages 部署）
   - 采集任务说明（L4 机器：扫描 GitHub/arXiv/推文 → 生成热词卡 → 写入采集/）
   - 成熟度升降级流程（hot → stable 的触发条件）
   - 回滚与修订（git revert 机制）

4. **docs/index.md** —— 分类索引页（入口地图）：
   - 按分类列出词条（当前 3-5 个示例词条：LoRA、VAE、蒸馏、GGUF、MoE）
   - 每个分类一句话说明
   - 顶部说明双结构（沉淀层/采集层）
