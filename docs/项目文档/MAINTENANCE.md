# MAINTENANCE — 维护流程

> 面向 L3 核心维护者与 L4 采集 Agent。依据 DESIGN-SPEC.md，冲突时以它为准。

---

## 一、审校流程（质量门四道）

内容进站走四道门，每道门都是硬关卡：

1. **起草**：AI / 贡献者写第一稿。AI 生成内容标注 [AI]，人工审校过标注 [人]。
2. **自动校验**：CI 跑 Schema 校验（必填字段 + 链接有效性 + 格式检查）。未过 → 自动打回，维护者不介入。
3. **人工审校**：维护者逐条审读，把关三件事：
   - **读感**：人话优先做到了吗？一段话能看懂吗？术语首次出现带全称了吗？
   - **判断**：论断与 `sources` 对得上吗？争议观点是否平衡呈现？
   - **取舍**：该收录的深讲，不该收录的打回或建议进采集区。
   维护者可以直接改稿，也可以在 PR 里提意见让贡献者改。
4. **定稿发布**：审校通过 → `status` 改为 `published` → 合并 → 站点自动重建。

审校记录留在 PR 讨论和 git 历史里，信任靠留痕。

---

## 二、发布流程

1. 词条 PR 合并进主分支。
2. CI 触发：先跑 `validate.yml`（Schema 校验），再跑 `pages.yml`（GitHub Pages 部署）。
3. 站点自动重建，词条上线。无需人工操作。
4. 若校验意外失败：不合并，回 PR 修；若部署失败：查 CI 日志，重跑 workflow。

---

## 三、采集任务（L4 机器）

采集 Agent 是「社区感知层」，只负责发现，不负责沉淀。

- **扫描源**：GitHub 趋势、arXiv 新论文、大 V 推文、Reddit / RSS 讨论。
- **产出**：热词卡——新概念、新动向、争议话题。
- **写入位置**：只允许写入 `采集/` 目录（未沉淀区）。**机器永远不直接写 `docs/词条/`。**
- **边界**：热词卡只是线索，不是词条内容。升级为正式词条必须走 L2 草稿 → 校验 → L3 审校的完整流程。

---

## 四、成熟度升降级

### 升级：hot → stable
触发条件（缺一不可）：
1. 词条积累 **≥2 个独立来源**（同一作者的不同转载不算独立）；
2. 维护者审校通过——完整定义、多源交叉验证、无悬而未决的重大争议。

操作：改 `maturity: stable`，删掉定义区顶部的 [热词] 热词警示条，`updated` 更新为当天，`revisions` +1，走 PR 合并。

### 降级：stable → hot
触发条件（任一即可）：
- 来源失效或被证伪，剩余来源不足 2 个；
- 技术事实发生重大变化（如方法被官方弃用、定义被社区推翻）；
- 词条被可靠来源指出存在重大错误。

操作：改 `maturity: hot`，加回热词警示条，并在 PR 说明降级原因。

---

## 五、回滚与修订

- **日常修订**：改内容走 PR，合并前把 `updated` 更新为当天、`revisions` +1。修订历史由 git 天然留痕，不在词条里手写改动日志。
- **错误回滚**：合并后发现严重错误，用 `git revert <merge-commit>` 回滚，再修好后重新提 PR。不要 force-push 抹掉历史——信任靠留痕，历史不能消失。
- **全站回滚**：若部署出问题，revert 到上一个可用的合并提交，重新部署即可；词条内容以 git 历史为准，站点只是渲染结果。
